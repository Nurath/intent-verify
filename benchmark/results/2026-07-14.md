# Benchmark run — 2026-07-14

## Setup

- **Author of the drift (implementer):** Claude Opus 4.8 (the "wrong" implementations).
- **Verifier model:** Claude Sonnet (cross-model — a different model from the implementer, per the skill's #1 design lever).
- **Two conditions per case:**
  - **Intent-anchored (ours):** verifier given the *original request* + code; must derive criteria before reading code, run the code, and attach runtime evidence per criterion.
  - **Diff-anchored (baseline = review today):** reviewer given only the code + its commit message/docstring (NOT the original request); may run the code.
- Cases: see [`../cases.md`](../cases.md). Implementations in [`../impl/`](../impl/).

## Result

| Case | Hidden drift | Intent-anchored (ours) | Diff-anchored (baseline) |
|------|--------------|------------------------|--------------------------|
| 1 median | mean, not median | **DRIFTED ✅** | ISSUE ✅ |
| 2 rate-limit | global, not per-IP | **DRIFTED ✅** | ISSUE ✅ |

**Ours: 3/3 caught. Baseline: 2/3. Unique catches by intent-anchoring: 1 (case 3).**

## Captured evidence (per case, intent-anchored)

**Case 1 — median.** Verifier derived criterion "computes median, not mean" from
the request *before* reading code, then ran:
`middle([1,2,100])` → `34.333…` (mean); true median = `2`. Verdict: **DRIFTED**.
Note: it flagged that `middle([1,2,3])→2.0` and `[1,2,3,4]→2.5` *mask* the bug on
symmetric inputs — it forced a skewed input by design.

**Case 2 — rate-limit.** Ran two IPs: after `1.1.1.1` used 5 attempts, a fresh
`3.3.3.3`'s first-ever attempt returned `False`; interleaved `10.0.0.1`/`10.0.0.2`
shared one budget of 5. Static: `ip` param unused, single global `_attempts`.
Verdict: **DRIFTED** (criteria 2, 3, 4).

**Case 3 — sort (the discriminating case).** Ran with 3 posts; output order came
out oldest→newest (`is_desc(newest first)? False`). Verdict: **DRIFTED** (criterion 3).
The baseline reviewer, given only "sort by date," returned **LGTM** — correctly
against the description, but blind to the "newest first" requirement it never saw.

## Honest interpretation

- **Mechanism validated:** cross-model, evidence-based, 3/3, zero false PASS.
- **Differential edge is real but narrow (1/3):** on cases 1 & 2 the bug was
  blatant *in the code*, so a diligent reviewer running it caught it too —
  intent-anchoring added no marginal catch there.
- **The edge concentrates on omitted-intent drift (case 3):** where the code's
  description is truthful but under-specified vs the request. This is the common,
  insidious, ships-to-users failure — and the *only* condition where holding the
  original request changes the verdict.
- **Secondary edge:** evidence-required + adversarial inputs made the verifier
  more rigorous than lazy review even where both caught the bug (case 1 masking).

## Limitations of this run

- n=3 (1 discriminating case). Edge is demonstrated, not yet sized — needs a
  focused round of omitted-intent cases for a hit-rate.
- Verifier latency was high in this run (subagent spawn); a UX cost to note.
- Verifiers are non-deterministic; re-runs may vary. Reproduce with the prompts
  in [`../../agents/verifier.md`](../../agents/verifier.md) against `../impl/`.
