# 2026-10-06

Two releases, and most of a third. 0.4.2, a correctness release after a second
independent review and two adversarial passes. 0.4.3, after a third review the
same evening. And the work for 0.5.0, after the plugin's first use on real
work: one question before verifying, the ledger printed in the report, and
agents that no longer run at the session's effort. That one was not released
this day; the last section is where it stood, and `logs/2026-10-07.md`
continues it.

## Why

The maintainer had 0.4.1 reviewed with a different vendor's model, at commit
`382c32e`, against the first review of 0.2.0. It confirmed the earlier findings
as addressed and reported three new ones in the JSON ledger path added the day
before. All three reproduced on `main`. The maintainer chose to fix all of them
and ship by PR, merged on green CI, and then to fix whatever an attack on the
fix found and release.

## What the review found

| | Finding | Reproduced |
|---|---|---|
| P1 | A repeated JSON key hides a verdict: `"verdict": "FAIL", "verdict": "PASS"` read as PASS, because Python's decoder keeps the last key | yes, exit 0, MATCHES INTENT |
| P1 | Two ledgers carrying the same nonce: a PASS ledger, "Correction:", a FAIL ledger validated as the first | yes, exit 0, MATCHES INTENT |
| P2 | Truthful output made only of field-looking lines (`FINAL: MATCHES INTENT`) was rejected as no evidence, because a JSON ledger was rewritten as text to be checked | yes; no retry could fix it |

The same two weaknesses reached further than the review listed: a repeated
`criteria`, `final` or `out` key in a ledger, and in stage 1 a draft manifest
winning over its correction, or a repeated key in a manifest.

## First fix, and what attacking it found

The first fix kept the version 1 object and made the parser stricter: repeated
keys are defects, exactly one top-level ledger may carry the nonce, and a JSON
ledger is checked as data and not rewritten as text. It passed its own tests,
the review's fixtures, a replay of every stored reply, and a 16 + 3 case run on
real models.

Then a second model (Sonnet 5.5; the fix was written by Opus 5.5) was given
the code, the rules and the threat model, and no conclusions. It reported
thirteen findings. All reproduced.

| | Finding | Kind |
|---|---|---|
| F1 | A second conclusion that does not parse as a top-level ledger is not counted: a correction with a trailing comma, one cut off halfway, one without its `ledger` key, one nested under a `correction` key, or a second verdict under `Verdict` / `verdict_corrected` / `Final` | false pass |
| F2 | Output pasted with an unescaped double quote ends its string, supplies passing verdicts and closes the ledger; the verifier's real remainder is left over as text | false pass |
| F3 | Text ledger: in a copy the harness indented, a forged ledger behind carriage returns stood at column 0 | false pass |
| F4 | A run of more than 4,300 digits in a criterion number or in the final line raised `ValueError` | crash |
| F5 | The object scanner took time quadratic in the number of unclosed braces | stall |
| F6 | `--manifest ""`, `--request ""` and `--nonce ""` were read as "not given" | fail open |
| F7 | Half of a surrogate pair in a manifest was reported as "not a run directory" and left a cut-off file | wrong error |
| F8 | Ledger and manifest criterion texts were compared ignoring case | weak check |
| F9 | The final line was checked by how it starts: `MATCHES INTENT — DRIFTED: criterion 1 failed` matched | false pass |
| F10 | A zero-width space counted as output; the run's nonce inside a command was accepted | weak check |
| F11 | Quotes `"a"`, `"the"` and `"ort"` (inside `sorted`) were accepted; a criterion `id` of `true` passed; curly quotes and NFC/NFD differences were rejected | both ways |
| F12 | A raw line break inside a JSON string produced a retry message that did not say what to change | misleading |
| F13 | `--manifest-from` dropped `- #tags are lowercased` as a heading | data loss |

F1 and F2 showed that the first fix had the wrong shape. It counted what
parsed, and the dangerous replies were the ones that did not parse, or parsed
as something the verifier never wrote.

## Changes shipped — 0.4.2

The format changed instead of the parser growing more cases.

- **Ledger version 2** (`agents/verifier.md`, `tools/validate_ledger.py`):
  `{"ledger": 2, "nonce", "mode", "criteria", "final", "observations", "seal"}`.
  - The reply is the object: its first `{` opens it and nothing may follow the
    closing brace, a code fence aside. One decoding attempt, no scanning.
    Remarks moved inside, to `observations`.
  - `seal`, the last key, repeats the nonce, and the nonce occurs nowhere else
    in the reply.
  - Keys are allowlisted at the top and per criterion. No key twice.
  - All-PASS needs `final` to be exactly `MATCHES INTENT`.
- **Shared rules** (`_check`): criterion text compared letter for letter
  (spacing and Unicode composition aside); evidence that shows nothing is
  missing; numbers of at most six digits.
- **Text ledger**: a carriage return alone no longer ends a line.
- **Stage 1** (`check_manifest`): the reply is the manifest and nothing after
  it; keys allowlisted; an `id` is an integer; a quote is four characters or
  more and occurs in the request as whole words, ignoring case, spacing, curly
  quote marks and composition.
- **Command line**: an empty argument is a usage error; `--nonce` must be 16 to
  64 hex characters (`--begin-run` makes 32, the M4 runs of 2026-10-05 used
  16); exit 3 when the validator itself fails; `--unsealed` checks a
  version 1 ledger, so that the two runs kept from 0.4.0 and 0.4.1 stay
  checkable (a test runs both).
- `benchmark/run_bench.py` writes sealed ledgers for the simulated verifiers;
  the forged-ledger fixture prints a version 2 object with a seal of zeros.
- `skills/intent-verify/SKILL.md`: never repair a reply; report the ledger's
  observations; exit 3.

## Tests / verification

- 250 unit tests (were 209), hook selftest 34 of 34, mock benchmark exit 0.
- Every finding above has a regression test (`TestSealedLedger`,
  `TestSecondReview`, `TestAdversarialPass`), and a scratch script reproducing
  all thirteen against the first fix now reports each one closed.
- **The paste-injection property.** A first version pasted random pieces of
  ledger syntax into a failing ledger, 12,000 replies. It found nothing, and it
  still found nothing with every protection switched off, so it tested nothing.
  The test that replaced it enumerates a small grammar (end the string, maybe
  the entry, forge later entries, end the list, conclude, close or open
  something for the real remainder): 4,680 replies, none validates as
  `MATCHES INTENT`, and 76 of them conclude `MATCHES INTENT` and are stopped by
  the seal and the text-after rule alone. The test asserts that count, so it
  fails if the grammar stops containing a working attack.
- **Replay.** Every stored real reply through the new validator, compared with
  the verdict its run recorded: the 124 recorded before this release (53
  version 1 JSON ledgers, checked with `--unsealed`, and 71 text ledgers) all
  reproduce, and the 78 stage-1 replies still validate.
- **Real models with the sealed format** (`claude -p --safe-mode`, cost at list
  price). The record is `benchmark/results/2026-10-06-sealed-ledger.md`.
  - Live, end to end: a headless session with the working tree as a plugin.
    The hook filed the verifier's reply and `--run` validated it, DRIFTED on
    the `median` fixture. Kept as `benchmark/results/2026-10-06-sealed-live.raw/`.
  - Sonnet 5.5, controlled set, two-stage: 16 of 16, no retries, $1.27.
  - Sonnet 5.5, adversarial set: 3 of 3 DRIFTED, no retries, $0.29.
  - Haiku 4.5, STRUCTURED, criteria held fixed: a valid ledger on the first
    reply 16 of 16, expected verdict 15 of 16. The one INCONCLUSIVE is the
    five-criterion budget on a six-criterion manifest, as on 2026-10-05. $1.08.
  - All 20 Sonnet replies were the object alone, with exactly the format's
    keys. Haiku fenced all 16 and opened one with a sentence.
- **Second adversarial pass**, on the rewritten code, by a third model (Fable
  5.1), with the code, the prompts, the threat model and the list of what was
  known. No false pass, no crash, no unfixable false reject, and no way to the
  version 1 rules without the flag. Two minor findings, fixed with tests:
  `--manifest-from` wrote a manifest it later rejected (a line holding only a
  zero-width space), and a brace in the sentence before the ledger produced a
  defect that pointed at the nonce.

## A third review, and 0.4.3

The maintainer had 0.4.2 reviewed the same evening, at `76fb7aa`. The review
re-ran the three findings of the second review against the new format (all
rejected or, for the truthful-output case, accepted as they should be),
replayed the 37 version 2 replies published that day, and reported one new
finding.

| | Finding | Reproduced |
|---|---|---|
| P2 | The nonce check counts the nonce in the reply as written. `"cmd": "python t.py --token 0123456789\u0061bcdef..."` decodes to a command holding the nonce, and the reply still shows it only twice | yes, exit 0, MATCHES INTENT; the literal spelling exits 1 |

It reached further than the fixture: the same spelling got through in `out`,
`reason`, `observations` and a criterion's text, in a version 1 ledger with
`--unsealed`, and an upper-case copy of the nonce got through in any field and
in a sentence before the ledger.

Asked how to ship it, the maintainer chose 0.4.3 by PR, merged on green CI,
with an adversarial pass first.

### Changes shipped — 0.4.3

- `tools/validate_ledger.py`: the nonce is counted in the raw reply in either
  letter case, and in every decoded string of the ledger, keys included
  (`_strings`, a loop and not a recursion, since a reply decides how deep a
  value goes). Either count above what the format allows is a defect.
- Tests: the review's case in every string field, in both spellings and
  against a control (another 32-hex token is not the nonce); the version 1
  path; values nested thousands deep.
- The verifier's prompt is unchanged, so no model run was repeated.

### Tests / verification

- 254 unit tests, hook selftest 34 of 34, mock benchmark exit 0.
- The review's fixtures: the escaped one exits 1 (was 0), the literal one 1,
  and the three from the second review as before.
- The new regression test fails with the decoded check switched off and
  passes with it on.
- Replay: all 161 recorded verdicts reproduce.
- **Adversarial pass on the fix** (Sonnet 5.5; the fix was written by Opus
  5.5), narrow: the nonce rule and whatever the change might have broken. It
  found:
  - P1, and in 0.4.2 too: the nonce was counted over the whole reply, so the
    count could be balanced. `Run <nonce> done.` in front of a ledger whose
    `"seal"` is spelled with an escape shows the nonce twice, as expected, and
    validated. Fixed by locating the nonce: none around the ledger, none in
    its decoded strings besides the two values, and those two written out.
  - P2, older than this change: the check on what follows the object was
    quadratic in a run of white space (80,000 line breaks, 14 s). Fixed.
  - P3, `--unsealed` only: the search for a version 1 ledger could be made to
    rescan a long tail 2,000 times. The limit is 200 now.
  - No false reject (it checked every Unicode code point for lower-casing
    surprises) and no crash.
- The pass's own fuzzers, which compare the validator with an independent
  oracle, were then run against the final fix: 94,976 sealed and 23,744
  version 1 combinations with no reply that validates while holding the nonce
  out of place, and 100,000 mutation rounds with none either. Its 18 truthful
  controls still validate.

## 0.5.0 — one question first, and minutes less

Built and measured this day on the branch `feat/v0.5.0-ask-first-faster`.
Nothing was committed.

### Why

The maintainer asked whether the other project's session had used the plugin
properly. Its transcript showed that it had followed every step. What was
wrong was the plugin's own doing:

- **Fourteen minutes.** 2 min 44 s for the criteria and 9 min 12 s for the
  verifier. Both agents inherited that session's maximum effort, and the
  selector's answer was the most capable candidate.
- **Three selector calls** before it answered: the registry knew neither
  `claude-opus-5-5` nor the names Claude Code uses.
- **A one-line report.** "Passed all 4 criteria", without the ledger.
- **The wrong question went unasked.** The ambiguity the criteria agent
  recorded was whether one sentence was the user's decision at all. Every
  criterion passed under the reading that it was, so nothing was asked. On the
  other reading no change had been requested yet.

Asked to work on it, and to cut tokens and time where that could be done, the
maintainer was given three choices and took: ask before verifying (not after
the verdict, not a louder caveat); the validator prints the ledger (not
stronger wording alone); and, after asking which efficiency changes would be
effective and getting them ranked with numbers, the three that are (the
verifier on the fastest measured model, both agents pinned to high effort, the
criteria agent on Sonnet), leaving CLAUDE.md loading as it is.

### Changes — 0.5.0

- `agents/criteria.md`: one ambiguity may carry `"whether": true`, with the
  rules for when (a question, a request for an explanation, a choice not made;
  never a request in the form of a question or a rule stated as a fact).
  Frontmatter pins `model: sonnet` and `effort: high`.
- `agents/verifier.md`: `effort: high`. No model: the session names the
  selector's choice.
- `tools/validate_ledger.py`: `whether` in the manifest check (true or false,
  at most one, must name criteria, question and reading must show something),
  printed as `ASK FIRST:`; the ledger printed after `VALID`; everything printed
  that a reply or a request supplied goes through one filter (`_one_line`).
- `skills/intent-verify/SKILL.md`: the `ASK FIRST:` step with its four
  outcomes; the selector in one call; "show the block as the validator printed
  it"; no model or effort chosen for the criteria agent.
- `tools/select_verifier.py`, `models/registry.json`: `--prefer fast|capable`,
  `verify_seconds`, the current Claude models and Claude Code's own names.
- `hooks/capture-intent.js`: `--list` names the Python command that works.
- `benchmark/run_bench.py`: `--effort`, high by default. New:
  `benchmark/ask_first.py` and its 17 requests.

### Tests / verification

- 285 unit tests (were 254), hook selftest 35 of 35, mock benchmark exit 0.
- Replay: all 180 recorded verdicts reproduce (161 from before, 19 new).
- Measurements, all in `benchmark/results/2026-10-06-faster-and-ask-first.md`:
  - one task before and after from a maximum-effort session: 281 s and $1.08
    for the two agents became 40 s and $0.06, same verdict;
  - the effort pin by itself, two plugin copies differing in one line: 437
    output tokens with it, 15,863 without, so Claude Code 2.1.292 honours it;
  - controlled 16 of 16 and forged-ledger fixtures 3 of 3 at the pinned
    effort, no question asked before verifying on any;
  - the question: marked 21/21 where the words may not ask for a change, 0/27
    and 0/26 where they do.
- **Adversarial pass on the two additions** (Sonnet 5.5; the code is by Opus
  5.5). The body of the printed ledger and the rule for the marked ambiguity
  held. Five findings around them, all fixed with tests: the conclusion on the
  `VALID:` line and the questions of `--check-manifest` were printed as
  written, so escape codes could redraw them on a terminal; a question that
  shows nothing was accepted; combining marks were unlimited; a huge value was
  flattened whole. Its reproductions and fuzzers were run again after those
  fixes.

### Mistakes made while measuring

- **A label written after seeing the answer.** The first look at the question
  missed one request in six. It had been labelled "must ask"; run again, the
  same request got the other answer, and a careful reader could take it either
  way.
  It is now labelled so and not scored, and every request is run three times.
- **Rules fitted to the author's own requests.** The rules of the criteria
  agent were revised twice after misses on the 17 requests written to test
  them, by the same session that wrote the rules. The published numbers say
  so. Before the third run a stop rule was fixed (no revision after it,
  whatever it showed), and requests the rules had never seen were added, with
  the expected answer written down first.
- **A timing from the wrong effort.** The registry's `verify_seconds` for
  Sonnet was first taken from 0.4.2's run, which ran at the CLI's default
  effort. The agents now run at high, so it is the 12.5 s of the re-run.
- **An overstated sentence** in the changelog draft said capability above the
  floor "did not change a verdict on the measured sets". One task was run on
  both models. It now says that.
- **The pin was nearly released unchecked.** A frontmatter field Claude Code
  does not recognise is ignored silently, and the before-and-after changed the
  model and the effort together. The two-copy check was added late, and is the
  only evidence that the field does anything.

### The change checked against its own request, round 1

`/intent-verify` was run on the change with the installed 0.4.3, in the
session that made it.

- **The request has no subject of its own.** "ok lets work on it and can we
  also make improvements ..." answers an offer in the assistant's previous
  message. That paragraph was copied from the transcript into the frozen
  request, labelled as not the user's words, ahead of the three captured parts
  (the task and the two sets of answers). The skill does not say what to do in
  this case.
- **Stage 1:** 15 criteria, each with a quote, no ambiguity. With the unpinned
  agent on Sonnet 5.5 at this session's maximum effort it took 307 s and
  50,293 tokens.
- **Stage 2** (Sonnet 5.5, FULL): 36 tool calls, 176,220 tokens, 12 min 18 s.
  The hook filed the reply, and the installed validator read that copy:
  `VALID: 15 criteria (all 15 manifest criteria covered), final = MATCHES
  INTENT`.
- **What the observations said that the verdict did not:**
  1. Criterion 14, "for complex changes the selector still picks the top-tier
     model", passed on the reading that top tier means T1. A complex change
     written by Opus got Sonnet 5.5 all the same, because Fable 5.1 has no
     score to rank by, and `--prefer capable` changed nothing. The option the
     maintainer chose had said "Sonnet instead of Fable when Opus wrote the
     change ... Complex changes still require the top tier".
  2. The printed ledger cut the observations at 800 characters. They were
     4,536 long, and the cut fell in the middle of the caveat above.
  3. Criterion 15 says neither agent skips CLAUDE.md. The criteria agent has
     skipped it since 0.3.0, and the change does not touch that; the verifier
     judged it against the user's words ("leaves CLAUDE.md loading as it is")
     and said so. The criterion over-claims; the code does not drift.
  4. The registry's timings could not be traced to a published file. They are
     in the results record now.
- **The tree was edited while the verifier worked** (the registry's timing, one
  test line, the documents). It noticed, took a snapshot and checked it by
  hash. Finish first, then verify.

Fixes for the first two were half made when the maintainer said to stop for
the day.
