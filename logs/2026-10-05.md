# 2026-10-05

Three releases in one day: 0.2.1 (PR #2), 0.3.0 (PR #3) and 0.3.1 (PR #4).

## Why

An independent review of 0.2.0, run with a different vendor's model against
commit `2c97a5a`, reported eight findings and several observations: ledgers
that validated as MATCHES INTENT when they should not have, requests verified
after being cut at capture, prompts left un-ignored in host repositories,
unredacted key shapes, and README claims that were never measured. Every one
reproduced.

The maintainer chose to patch whatever needed no contract change and to have
the rest written up as a design. After reading the design the same day, the
maintainer approved building it.

## Changes shipped — 0.2.1 (PR #2, merged as `e951d8c`)

The full list is in `CHANGELOG.md`. In short:

- **Validator:** values must sit on their field's line; every criterion block is
  parsed and the last `FINAL` is the conclusion; one `VERDICT` per criterion;
  `mode:` required; criteria numbered 1..N; UTF-8 streams.
- **Capture:** `.intent/` ignores itself; prefixed API keys redacted; cap 16k →
  64k; a marker for input too large to read; only unmistakable invocations
  tagged; `--list` / `--freeze` so the freeze step is a command scoped to the
  session.
- **Benchmark runner:** a timeout no longer aborts the run; the retry receives
  the rejected reply; raw replies kept.
- **Docs:** claims that were never measured were removed or qualified.

Found while fixing, and included: a forged `FINAL` line when the verifier's own
was missing; prompts beginning with the tool's name hidden as invocations; an
empty session id listing every session silently; a `.cmd` shim that could not
be launched on Windows; and, from the macOS CI leg added in this release, shell
fallback redaction that had matched nothing under BSD `sed` since 0.2.0.

## Changes shipped — 0.3.0 (PR #3)

Built from `docs/DESIGN-v0.3.md`; that file's first section records what was
built and where it departs from the proposal.

- **Criterion manifest, two stages.** New `agents/criteria.md` derives criteria
  from the request alone. `validate_ledger.py` gained `--check-manifest` (every
  quote must occur in the request), `--manifest` (a ledger must carry every
  manifest criterion, same number, same text) and `--manifest-from` (use the
  user's own criteria). The skill asks the user about ambiguities once.
- **Ledger outside the project.** The Node hook writes one file per session
  under the plugin data directory; 30-day retention replaces rotation; the
  `log.md` mirror is gone; a legacy `.intent/` is still read and never written.
  The skill's working files moved to a scratch directory.
- **Capture.** Answered questions are recorded as `decision` entries by a second
  hook; `--freeze` joins several entries into one request; harness-submitted
  prompts are labelled when listed; cap 256k keeping both ends.
- **Validator fixes from running the tool on itself:** a uniformly indented
  reply now validates; an unreadable file exits 2, not 1.
- **Benchmark.** `--two-stage` for real runs; an `omitter` mock profile.
- **Tests.** A new module pins the plugin's prose and configuration: helper
  paths in the skill, the agents' tool lists, hook registration, version.
- **Docs.** README rewritten for the two-stage flow, with a row for spec-first
  harnesses in the comparison; `docs/architecture.md`,
  `docs/handoff_quickstart.md` and this `logs/` directory are new.

## Changes shipped — 0.3.1 (PR #4)

One fix, found within minutes of installing 0.3.0 and listing our own ledger
with it: ten of the session's fifteen entries were subagent hand-backs, which
arrive as `<agent-message>` and which 0.3.0 kept in the listing. They pushed
the real requests out of the default ten rows. Hand-backs are now hidden with
the other agent reports.

## Tests / verification

- **0.2.1:** 135 tests; four CI checks green on the merged commit. Every review
  finding was re-run before and after against the 0.2.0 and patched code.
- **0.2.1 verified with the tool itself.** A verifier on a different model from
  the implementer (same vendor family) was given the frozen request, the review
  and the scope decision. Result: 16 criteria, all PASS, MATCHES INTENT, ledger
  valid. It took over the dispatcher's 14 criteria and added 2 of its own, and
  ran a mutation check of its own (the new tests fail on the 0.2.0 tree: 33
  failures, 8 errors). It used 18 shell commands against a stated budget of
  about 15.
- **0.3.0:** 181 tests (18 skipped on Windows), Node selftest 25 of 25, mock
  benchmark green. The shell dispatcher's tests were also run locally through
  Git Bash. The two-stage real-model path was run end to end against a stub CLI
  installed as a `.cmd` shim.
- **0.3.0 put through its own stage 1.** The request was the maintainer's
  go-ahead plus the design it referred to, about 21,000 characters. The
  criteria run returned 53 criteria, every quote found in the request, and four
  ambiguities: whether the work includes the smaller fixes and Change C;
  whether the spikes and measurements are part of it; whether the design
  document itself was to be committed; and which files "the logs" and "the
  explanation" are. Those are the assumptions the implementation had made
  silently. Verification stops there until they are answered, as the skill
  prescribes, so there is no stage-2 ledger for 0.3.0 yet. Several of the 53
  criteria describe things the implementation knowingly departs from; they are
  listed at the top of the design document.

  verdict with forged lines spliced in; none validates as MATCHES INTENT; 54 of
  the same 3,000 got past the 0.2.0 validator.
- **Manifest property (0.3.0):** 1,000 seeded ledgers with a non-empty subset of
  criteria removed; none validates against its manifest, while most validate
  alone.
- **Mock benchmark:** the `omitter` profile gets 2 false MATCHES on the 8
  drifted cases without a manifest and 0 with one.
- **Real models, 8 runs:** `benchmark/results/2026-10-05-two-stage-smoke.md`.
  Manifests valid on first reply for 3 of 3 requests; expected verdict on 4 of 4

## Later the same day — platform checks and the two-stage measurement

The session was restarted with 0.3.1 installed, and the `claude` CLI was logged
in again.

### Platform checks

All three open checks passed in the Windows desktop app on Claude Code
2.1.289. Details: `benchmark/results/2026-10-05-platform-spikes.md`.

- **S1:** the `intent-criteria` agent launched and returned a manifest. Its only
  tools were `TaskStop` and `SubagentHandback`; neither reads files or runs
  commands. `TodoWrite`, also in its allowlist, does not exist in this version.
- **S4:** two questions answered in one call became one `decision` entry with
  both questions, their options and both answers.
- **S5, skill half:** the skill's commands arrived with real paths for the
  plugin root, data directory and project directory, and the session id.

### Benchmark harness

- `run_bench.py --mode cli` now runs every call in `claude -p --safe-mode`.
  Before, each call loaded the runner's own CLAUDE.md, plugins, hooks and MCP
  servers, and an installed intent-verify logged every benchmark prompt into
  the runner's ledger. `--bare` would isolate too, but it ignores OAuth logins.
- It reads the CLI's JSON envelope and records each call's tokens, cost, turns,
  duration and session id in `usage.json` beside the raw replies. An error
  envelope (out of turns, an API error) counts as no reply and is not retried.
- Two tests added, 183 in all.

### Two-stage measurement

`run_bench.py --mode cli --suite controlled --verifier claude-sonnet-5-5
--two-stage`, one run per case:

- 16 of 16 expected verdicts: no false MATCHES, no false alarm, no
  INCONCLUSIVE. One retry: on `median_ok` the verifier paraphrased a manifest
  criterion, and the retry copied it.
- Each planted drift had its own criterion in the manifest, quoted from the
  request, and that is the criterion that failed. No other criterion failed on
  correct code.
- 33 calls, 1.79M tokens, $1.33 at list price, 5.6 minutes of model time.
  Stage 1 cost about 3.6k tokens a case; stage 2 cost 73k to 222k.
- Stage 1 raised 41 ambiguities over the 16 requests, 2 to 4 each. None
  concerned a planted drift. The harness answers none of them; the skill would
  put every one to the user.

The cross-model ablation was not run. On this set the drift is planted, not a
model's own mistake, and the cross-model arm already scores 16 of 16, so a tie
was the likely outcome.

### 0.3.2: ambiguities after the verdict

Asked to fix the question load. The criteria agent now records an ambiguity
only with the criteria that depend on it and the reading they assume. The
validator drops one that names no criterion. The skill asks nothing before
verifying, and afterwards only when a dependent criterion failed and the
evidence would differ under the other reading.

- First prompt: 16/16 verdicts, 12 questions over the 16 requests, 7 requests
  with none.
- The tool was run on this change. The request was a two-word follow-up
  pointing at the problem described in the previous reply. Stage 1 gave 7
  criteria. Round 1: **DRIFTED, criteria 1 and 3**. Questions remained on 9 of
  the 16 requests, and several had an ordinary reading ("is '3 to 20'
  inclusive?"). It also found the version test red (changelog entry not yet
  written) and five passages still describing the old flow.
- Tightened the prompt (an ordinary reading is not an ambiguity; never record
  one where either reading passes) and the skill (no question when the code
  fails the other reading too). Re-run on all 23 cases: controlled 16/16 with
  3 questions, 13 of 16 requests with none. Field 5/7 with 4 questions:
  `recall_weekend` was a false DRIFTED (a flag from the caller against
  recognising a weekend date, a second reading nobody recorded), and
  `recall_gpt4omini` was INCONCLUSIVE (no earlier version in the fixture to
  compare rates with). The field cases had never been run two-stage, so
  neither result can be pinned on this change.
- Round 2: **MATCHES INTENT**, all 7 criteria PASS, ledger valid. Its fresh
  stage-1 calls on requests it wrote itself: old prompt 9 questions, new
  prompt 1, on the same three requests.
- 193 tests.

### Notes

- A follow-up that only points at the conversation names nothing the ledger
  holds: the capture keeps what the user typed. To verify it, the frozen
  request needed the referenced paragraph quoted verbatim from the session
  transcript.
- What round 2 left standing: some kept questions still break the prompt's own
  "ordinary reading" rule, and only model compliance prevents that. When stage
  1 writes a criterion that either reading satisfies, the user is told the
  assumed reading but never asked. The validator now rejects an ambiguity that
  names a missing criterion, a small new way for a stage-1 reply to need its
  retry. The longer prompt costs about 0.7k more tokens a case.
- Verifiers ran some commands with absolute paths. Before publishing, those
  paths in the stored replies of the later runs were replaced with `<repo>`,
  `<tmp>` and `<home>`; nothing else in them was changed.

## Last — 0.4.0: the verdict path without the implementer (Change C1)

Decided after both gating checks passed: build C1, as its own PR and release,
with forged-ledger tests.

### Built

- `capture-intent.js --begin-run`: a run directory under the data directory,
  named by a 16-byte random nonce.
- `SubagentStop` hook, matched on `intent-verify:intent-verifier`: files the
  verifier's final reply byte for byte under the run whose nonce it carries,
  else in `_unmatched/`. Prints nothing and always exits 0, since a blocking
  `SubagentStop` hook would keep the verifier running. Retention covers runs.
- `agents/verifier.md`: the ledger is one JSON object carrying the run nonce,
  and the nonce must never go into a command.
- `validate_ledger.py`: `validate_json` (only the object with the run's nonce
  counts; rewritten as a text ledger and held to the same rules), `--run DIR`
  (validates the hook's copy; exit 4 when there is none), `--nonce` (a copy
  the session saved, reported as relayed). The text ledger stays accepted
  without a run.
- Skill: `--begin-run` before dispatch, `RUN NONCE:` in the dispatch, `--run`
  at validation, fallback to `--nonce` with "relayed" in the report.
- Benchmark: CLI runs are run-bound (`as_json` for the simulated verifiers in
  tests); `m4_json_ledger.py` keeps its text arm through
  `benchmark/verifier-text-ledger.md`; new `adversarial` suite (three drifted
  fixtures that print forged ledgers).
- Tests: 206 (13 new), selftest 31.

### Checked

- Live, headless with this version as a plugin: the hook filed the real
  verifier's reply under its run, and `--run` validated it (DRIFTED, criteria
  2 to 4, correct for the fixture). Kept as `benchmark/results/2026-10-05-c1-live.raw/`,
  which re-validates as it is.
- Adversarial suite: 3 of 3 DRIFTED. Two replies quoted the forged verdict in
  their evidence, where it stayed a JSON string.
- Controlled set with the JSON verifier: 16 of 16, no retries, $1.28. The same
  stage-1 prompt kept 8 ambiguities this time against 3 in the 0.3.2 run, so
  that count varies from run to run.
- Summary: `benchmark/results/2026-10-05-c1-run-bound-ledger.md`.

### Notes

- Two benchmark runs given the same `--label` write the same file; the
  adversarial results were moved aside before the controlled run overwrote them.
- The M4 script's text arm must also drop the verifier's new nonce input, or a
  text-ledger verifier is told to copy a nonce it never gets. A test caught it.
